3 · The non-negotiables — memorize these six

If you remember nothing else, remember these. Each has been violated at least once and is now audit-blocked.

1 · Lavender is Arth, and only Arth. --lav #BDB3F6 and the waterline glyph appear only where the AI is speaking. On a link, a chart segment, or a state pill, it is a review blocker. (Broken 4× historically — stage pills, allocation bar, island empty-state, report "Missing" rows. All fixed.)
2 · Color is state, never decoration. --pos/--watch/--attn/--neg mean GOOD/WATCH/ATTENTION/CRITICAL, locked to the Rule Book bands. Anything "highlighted" without a state takes bone at low opacity. NO DATA must never look like a passing state; ERROR must never look like NO DATA. Cost items cap at ATTENTION — never CRITICAL.
3 · No new tokens, fonts, icons, or themes. Tabler icons only, no emojis. One accent (bone). No light theme in beta. A raw hex outside the token sheet is a review blocker.
4 · Motion is water: no bounce, spring, overshoot, spinner, or count-up. Views surface (rise + fade). Arth thinking = the N-loader. Errors and NO DATA get no animation — stillness is the signal. prefers-reduced-motion kills all of it.
5 · Every line carries a number or ends in an action. "Your portfolio needs attention" is banned. "Card at 42% leaks ₹1,840/mo — clear it, save ₹22,080/yr" is the house voice. App speaks to the client (second person); the CRM speaks about the client (third person).
6 · One .cta per screen. Reuse an existing component before drawing anything. The inventory is in the Design System §4 — cards, rows, pills, CTAs, fields, OTP boxes, depth gauge, vessel, consent gate, waterline divider, chat bubbles, kanban, Arth rail.

5 · The build procedure — every request, every time

This is the change protocol from the UX Architecture, condensed to the steps you actually perform. Follow it even when the request comes from leadership, even when it seems trivial.

FROM REQUEST TO SHIP

1 · Restate. Write the request back in one line. If it is ambiguous, ask before anything else.
2 · Classify. Reuse existing component (build it) · variant of existing (build, note it) · genuinely new token/component/pattern (STOP).
3 · Cross-check. Does it conflict with a token, a component, or one of the ten UX principles? Name the exact rule — "it feels off" is not a citation.
4 · If it conflicts, STOP and confirm. Present the conflict, 2–3 options that honour the system, and the impact (screens touched, flows affected, one surface or both). The requester decides with full information. Never a silent change.
5 · Build with assertions, then run the full ship sequence below. Never crop the audit output.
6 · Bump all artifacts together — design file · flow doc · release note, same version number, IST timestamp, latest on top. Disclose every mistake you caught yourself, in the release note.
7 · Canonize. Anything genuinely new that survived sign-off gets written into the Design System in the same release. The system only grows through the front door.

5.1 · The ship sequence (from Design System §13.2 — do not skip a step)

1. Patch with explicit assertions (the anchor you edit must exist, or fail loudly)
2. Section-presence check — ALL screen IDs present (63 app / 13 console). A missing
   section is the failure mode that shipped silently before; this check is mandatory.
3. Handler reachability — every t.id=='x' branch maps to a real, tappable element
4. Runtime smoke test — execute the whole script against a stubbed DOM; no ReferenceErrors
5. Copy to outputs only after 1–4 pass, full audit output shown
Delegation rule: the click selector must keep covering all tap classes — .tap,.lnk,.seg span,[data-*]. New interactive components register a data attribute; they never invent their own handler. This is why a new button "just works" — don't break it.
