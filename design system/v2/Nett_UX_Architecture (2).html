NETT · UX ARCHITECTURE · FOR THE TEAM

How it behaves,
and why.

Design decides how it looks; this decides how it thinks. New pages must obey these principles the way new screens obey the tokens.

1 · The ten principles

1. Journey-first, never list-first. The system already knows the work — it presents an ordered day, not a database. Lists exist one level down, as reference. (This was learned the hard way: CRM v1 was list-first and got rejected. Rightly.)
2. Arth narrates, humans decide. The AI opens every surface with a made day, a suggested reply, a fit verdict — but the send button, the recommendation, and the responsibility belong to the human. Arth gives facts, fit, and sequencing; never scripts pretending to be advice.
3. One truth, two views. Client and RM see the same numbers, same bands, same report. The CRM never has a "better" version of reality — it has more context around the same reality.
4. Consent is architecture, not a checkbox. Unshared data doesn't exist for the viewer — structurally (no fields on the object), visually (below the waterline), and legally (only the client can action consent, on their own device, channel + timestamp stored). Behaviour signals follow the same switch.
5. Relevance floats. Latest consent, then waiting chat, then timed follow-ups — everywhere: the tide, the list default sort, the relevant-now strip. Recency of intent beats every other ordering.
6. Every line carries a number or ends in an action. The copy law, both surfaces. "Your portfolio needs attention" is banned; "Card at 42% leaks ₹1,840/mo — clear it, save ₹22,080/yr" is the house style.
7. Nothing unexplained. Every dot, pill, band and line is decoded in the Glossary, taught by the first-run tour, and answerable by asking Arth. If a new element needs explaining, its glossary entry ships in the same release.
8. Always a way back. Global history stack — every navigation, from any source (menu, Arth, cards, calendar), is reversible. Terminal states (paid, submitted) protect themselves with explicit exits instead.
9. Honest failure. Never blank, never silent: what failed, when, what you're seeing instead (last-good + timestamp), one Retry, a trace ID. Error ≠ NO DATA.
10. Gates still gate. Personalization (background, family, interests) shapes the conversation and the plan — it is never a shortcut past suitability. Hard gates (PMS ₹50L, AIF ₹1 Cr, waterfall rules) block in the copilot pre-sale and flag to Admin post-sale.

3 · Navigation & interaction model

PatternRule
History stackEvery navigation pushes; one global Back pops; login resets. Crumbs are secondary wayfinding on deep pages, never the only way out.
Action vs openEvery card separates the two: the primary button does the work; the Profile chip opens the person. Never make users choose between acting and understanding.
Ask as navigationAnything findable by menu must be findable by asking Arth in plain words. Unknown asks return capabilities, never dead ends.
Dual viewAny surface showing client data has a designed no-consent state — not an empty state: contact/comms/bookings stay workable; numbers sit below the waterline with the consent CTA.
RolesVisibility = assignment. Cross-service transparency within a shared client (who else, last talk) — never across clients. Admin sees all, and is read-only where acting would be impersonation (client chat).
Two-axis statusDeal stage and conversation health are separate axes; the red communication pill always outranks the stage for attention.

4 · The change protocol (use this when instructions conflict)

WHEN A REQUEST ARRIVES — ANY SOURCE, ANY SENIORITY

Step 1 — Understand & restate. Write the request back in one line. If it's ambiguous, ask before anything else.

Step 2 — Cross-check. Does it conflict with a token, a component, or one of the ten principles? Name the exact rule. "It feels off" is not a citation.

Step 3 — If clean → build. If it conflicts → STOP and confirm: present the conflict, 2–3 options that honor the system, and the impact (screens touched, flows affected, both surfaces or one). The requester decides with full information — that's respect, not obstruction.

Step 4 — Ship with discipline. Patch with assertions · run the full audit (full output, never cropped) · bump all three artifacts together (design · flow doc · release note; same version, IST timestamp, latest on top) · disclose every self-caught mistake in the release note.

Step 5 — Canonize. Anything genuinely new that survived sign-off gets written into the Design System file in the same release. The system only grows through the front door.

History says this works: four canon drifts occurred during the CRM build (lavender misuse, emoji icons, invented Arth mark, invented wordmark). All four were caught, fixed, and are now blocked by automated audit. The protocol isn't theory.

5 · From design to build — the spec contract

WHY THIS SECTION EXISTS (ADDED AFTER TEAM REVIEW — CREDIT: PM’S UX-SPEC PROMPT)

The first release of these docs had a hole, and the reason is structural: they were written from the prototype, and the prototype only draws read-only values. A box that never accepts input never forces the questions a build must answer — which control, when to validate, what empty looks like, what a partial scan costs. Demo data is always complete and never fails, so five whole categories of decision stayed invisible until the dev team’s spec prompt exposed them. This section canonizes them so web and app design always answer them up front.

RULE 1 — THE AFFORDANCE COMES FROM THE VALUE, NEVER FROM THE PICTURE

The prototype’s look carries (tokens, cards, type). Its input modes do not exist — every box is a drawing. Decide the control from what the value is:

ValueControl (canon)
Date the user recalls (birth, expiry)Wheel picker, named month on display (“14 Mar 1988”). A free-text date field with a format hint is never built — it accepts 31/02 and argues about slashes.
Date near today (appointment)Calendar picker
2–5 exclusive optionsSegmented control
6–15 options / 15+Menu / searchable list
Boolean acting at once / submitted with a formSwitch / checkbox
Bounded number nudged in stepsStepper (nominee %, SIP date)
OTP6 OTP boxes — canon digit count, both surfaces
Money / phone / PANText with the correct keyboard, shape-validated

RULE 2 — EVERY SCREEN SPECS FIVE STATES, OR ARGUES “CANNOT OCCUR”

EMPTY — copy plus the action that fixes it (blank is not a state, and NO DATA never reads as good) · LOADING — what’s shown, expected duration, can the user leave · ERROR — what failed and the exit (retry / continue / notify me) · PARTIAL — which data is missing, the confidence %, and the ₹ cost of the gap · DONE — the settled state. The prototype shows only DONE; the other four are where rework is born.

RULE 3 — RANGE VS RULE: PREVENT THE IMPOSSIBLE, EXPLAIN THE DISALLOWED

A future birth date is impossible — the picker must not reach it. Under-18 is policy — the picker reaches it and the field says “Must be 18 or older.” Never silently stop a range where a rule begins: silent ranges feel broken; explained rules feel fair.

RULE 4 — VALIDATION TIMING (DEFAULTS, OVERRIDE ONLY WITH REASON)

Text: validate on unfocus, then every keystroke until clean. Pickers and toggles: immediately. Cross-field rules: on submit. Input error copy names the fix, never the failure — “Enter a 10-digit mobile starting 6, 7, 8 or 9”, never “Invalid input.”

RULE 5 — PREFILL HAS PROVENANCE

A pre-filled value states where it came from (bureau, DigiLocker, AA), is as easy to clear as to accept, and never looks like the user typed it.

RULE 6 — UNSPECIFIED, NEVER BLANK

In any spec, an unknown is written UNSPECIFIED — a question the build asks before coding. A blank is a licence to assume. Where the build must decide anyway, it decides, ships, and flags: “Affordance chosen, not specified: ‹field› — spec shows X, I used Y because ‹reason›. Overrule me if X was intended.”

THE FIVE QUESTIONS — 90% OF REWORK DIES HERE

1. How is each value entered — the actual control, not “a field”? · 2. What’s on screen when there’s no data, and what action fixes it? · 3. What happens while it loads, and what’s the exit if it fails? · 4. Where does back go? · 5. Which limits are impossible vs merely disallowed?

Reconciliation note: the Design System says “reuse components”; the spec prompt says “never inherit from the prototype.” Both are right at different layers — the visual canon (tokens, shapes, type) always carries; the input affordance is never inherited from a read-only drawing. Look carries; input mode is decided from the value.
